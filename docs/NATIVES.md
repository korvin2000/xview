# Natives: sources, bundles, loader (PLAN P7)

> Status 2026-10-13: design accepted after two independent reviews (Opus, Codex); P7.1–P7.4 done: bundles published as GitHub release `natives-2026.10`, the default build downloads them and produces per-platform dist zips; Windows x64 verified end to end, Linux/macOS runtime pending the CI probe (P7.5). Facts below were verified by downloading the files and inspecting symbols/imports unless marked *(web only)*.

So the design's value is: one loader, a persistent per-user cache, per-platform packages instead of fat jars, and the small classes-only OpenCV jar. Only OpenCV, libavif and turbojpeg are custom builds, and no benchmark against the upstream builds exists. Hand-built files stay possible as an override (§5), the default is upstream.

JDK 26 ships `msvcp140`, `vcruntime140`, `vcruntime140_1` and `ucrtbase` in `bin/`, but **not `concrt140.dll`**: OpenCV (custom and WPILib alike) fails on a Windows without the VC++ 2015-2022 redistributable, and Media Foundation is missing on Windows N editions (Media Feature Pack). GitHub's Windows runners have the redistributable, so a probe there proves nothing about clean machines.

Rejected/not found: libjpeg-turbo 3.2.0 (JNA-only Java), official libavif releases (CLI tools only), Homebrew/MSYS2/Debian libavif (dynamic codec closures of 8+ libraries), FFM binding for TurboJPEG (deferred: `Linker.Option.critical` is unsuitable for long decodes, and 3.1.4.1 removes the need), Git LFS (client requirement, quota shared with forks), committing binaries, GitHub Packages (needs auth).

## 3. Distribution design
- **Repo holds metadata only.** `natives/<os>-<arch>.tsv`: one line per file — `file  sha256  size  url  member  version  license  deps`. It is the provenance record and the input of the bundler.
- **Bundles.** `tools/natives/bundle.sh` (maintainer or `natives-bundle.yml` on ubuntu) downloads each upstream asset, verifies its hash, extracts the member (`7z`, `dpkg-deb`/`ar`, `pkgutil`/`7z` for `.pkg`, `unzip` for wheels/jars), renames to the load-time file name, runs `check-binaries.sh` (`llvm-readobj --needed-libs`/`--coff-imports`, `llvm-objdump --macho -p`, `llvm-nm`: self-containment against a per-OS whitelist, glibc floor, macOS minos, JNI export set vs the vendored `native` declarations), writes `libs/<os>/<arch>/natives.sha256` (`sha256sum` format), `natives.deps` and `THIRD-PARTY-NOTICES.md`, and zips `xview-natives-<platform>-<rev>.zip`. The zips are uploaded (all at once, then published) as assets of an immutable GitHub Release `natives-<rev>` of this repo.
- **Contributor build** downloads exactly one bundle zip (`download-maven-plugin`, sha256 pinned per platform in the pom, cached in `~/.m2`, Maven proxy/offline settings honored, existing-file verification on) into `${project.build.directory}/natives/`, or uses a local tree with `-Dxview.natives.dir=<dir containing libs/>`. The two manifest files are also packed into the app jar as `/libs/<os>/<arch>/natives.sha256|natives.deps`.
- **Dist zip** per platform (`maven-assembly-plugin`, after shading): `xanderview.jar`, `libs/<os>/<arch>/…`, `jrunner.json` (filtered per platform), launcher script, `LICENSE`, `THIRD-PARTY-NOTICES.md`. Cross-building all platforms on one machine works (`-Dswt.flavor=…`): Java is portable and the natives are prebuilt.

## 4. Loader (LibraryLoader) after P7.2
Contracts kept: public API (`loadLibrary`, `checkLibrary`, `tryLoadLibrary`), the directory names `libs/<os>/<arch>/`, the file-name candidates, the soft-fail semantics, `-Dxview.libs.location`/`XVIEW_LIBS_LOCATION`, the cache root `<AppData>/libs/<os>/<arch>/`.
- **Default location** when nothing is configured: the directory containing the jar if it has `libs/`, else the jar itself (`jar:`). `libs.properties` has no absolute path any more.
- **Manifest mode** (the source has `natives.sha256`): bundle id = first 12 hex of sha256(manifest text); cache dir `<AppData>/libs/<os>/<arch>/<bundle12>/`. Libraries are still copied lazily on first use: temp file → sha256 verified against the manifest → atomic move; an existing file in the bundle dir is trusted (one `stat` per library per start). If `System.load` fails on a present file, it is re-verified and recopied once. Bundle dirs are immutable, so installed versions coexist; no automatic sweeping (a 30-day-old running process must keep its unrequested libraries).
- **Authority.** For the default location the manifest packed in the jar is authoritative: a source whose manifest differs is reported as damaged and its files are not trusted. An explicit `-Dxview.libs.location` is the owner's override: its own `natives.sha256` is authoritative, a mismatch with the jar is logged once. File names in manifests must be plain names (no separators).
- **Legacy mode** (no `natives.sha256` in the source): today's flat directory + exact content compare, unchanged. The deployed `C:\Program Files\xview\libs` keeps working.
- **Dependencies.** `natives.deps` lines (`libjxl_jni.so: libbrotlicommon.so.1 libbrotlidec.so.1 libhwy.so.1 libjxl_threads.so.0.11`) plus the code map (`libavif` → `libgcc_s_seh-1` on Windows, `opencv_java460` → `concrt140` on Windows) are copied and `System.load`-ed first by absolute path; the dynamic linker then resolves the dependent's import by module name / soname / install name against the loaded image. File names must equal the soname/install-name leaf.
- **macOS:** after copying, the `com.apple.quarantine` attribute is removed (`Files.copy` may clonefile and keep it).
- **Diagnostics (B10):** `NativeStatus` logs one line per native listed in the jar's manifest: `not requested | loaded | missing | failed`, with the bundle id. Only SWT is fatal. `java -jar xanderview.jar --check-natives` loads every listed native headless and exits 1 if one fails (CI probe). Callers that must degrade: `ImageLoader.loadJpegImage` catches `UnsatisfiedLinkError` (B18) and falls back to ImageIO; `ScaleFactory` falls back to a Java resizer when OpenCV is unavailable (B3).
- **Outside the loader:** `Hasher` uses `XXHashFactory.safeInstance()` (same xxHash64, no JNI extraction, no Unsafe); the vendored 7-Zip init loads `libgcc_s_seh-1` only on Windows; JNA's `jnidispatch` still self-extracts (optional later: `jna.boot.library.path` to the bundle dir).

## 5. Owner workflows
- **Hand-built override:** put the files in a directory `X/libs/<os>/<arch>/`, run `sha256sum * > natives.sha256` there (or omit the manifest for legacy mode), start with `-Dxview.libs.location=X`. Replacing a file in a manifest directory without updating `natives.sha256` is detected (hash mismatch → that library soft-fails with a clear message).
- **Update a native:** edit the TSV line (url, member, version, sha256), run `tools/natives/bundle.sh <platform>`, upload the new bundle to a new `natives-<rev>` release, bump the sha256 in the pom.
- **Add a platform:** new TSV, new `swt-*` profile properties (`xview.platform`, `xview.libdir`), bundle, probe.

## 6. jrunner
jrunner takes one `jar`, copies `files` with their path relative to its config, and collects files once for all targets, so one config cannot describe six different jars (the shaded jar differs per SWT flavor). Maven therefore writes a filtered `jrunner.json` into each platform's dist directory (`jar: xanderview.jar`, `files: ["libs"]`, per-platform `update.url`), and `jrunner build --target <platform>` runs there. Proposed jrunner changes (its own repo): per-target `jar`/`files` or `{platform}` placeholders with per-target update packages; strip `com.apple.quarantine` on macOS installs; its README still describes the Control-click bypass that macOS 15 removed. Longer term, a platform-neutral app jar plus per-flavor `lib/swt-<flavor>.jar` on the `Class-Path` would allow one jar for all platforms.

## 7. Decisions (owner, 2026-10-13) and what is still open
1. The repo `korvin2000/xview` is public: release downloads work anonymously (verified), arm runners are free.
2. Licenses are not a priority (hobby, non-commercial); the generated `THIRD-PARTY-NOTICES.md` in each bundle is kept anyway. No repo `LICENSE` for now.
3. OpenCV on Windows x64: the owner's custom 3.4 MB DLL (re-hosted on the natives release), `concrt140.dll` is not bundled: OpenCV needs the VC++ 2015-2022 redistributable (or a `concrt140.dll` dropped into `libs/windows/amd64/`, the loader treats it as an optional dependency).
4. SWT Windows x64: **migrated to stock 3.135** (2026-10-13; both consults recommended it). The app compiles unchanged (public API only); `--check-natives` loads the four DLLs; a 20 s GUI run and a classpath launch **without** `--add-exports` threw nothing (3.135's `SWT_AWT` uses JNI, so the export and the `PlatformLaunch` restart are gone); `swt.autoScale=false` + `swt.autoScale.updateOnRuntime=false` keep the old pixel behaviour (SWT refuses `autoScale=false` under monitor-specific scaling). **Owner's visual checklist:** fullscreen toggle (Enter, double-click) 20×, every SPEC §5 key after a click, after Alt-Tab and after the Ctrl+O/Ctrl+D dialogs, 100%/150%/200% DPI and a second monitor, window size/position restore, a 40 MP JPEG as sharp as before (same decode denominator), minimize/restore, Esc/Exit saves state. Rollback = `git revert` of the P7 SWT commit (the 4.527 sources are in history).
5. JXL on macOS: **CI build of `jxl_jni`** (`.github/workflows/natives-build.yml`: libjxl v0.12.0, `BUILD_SHARED_LIBS=OFF`, target `jxl_jni`, macos-15-intel + macos-14, ad-hoc codesign; same decoder and speed as Windows). jxlatte (pure Java) rejected: single-threaded float planes, no benchmark, no published ImageIO artifact. Until the workflow has run and the dylibs are added to the macOS TSVs/bundles, `.jxl` files are skipped on macOS (`ImageLoader` catches `LinkageError`).
6. jrunner runtime: JDK 26 (owner decision; non-LTS, so expect to move to 27 later).
7. Code signing: none (unsigned downloads; SmartScreen "Run anyway", macOS quarantine removal by the loader for the natives).
